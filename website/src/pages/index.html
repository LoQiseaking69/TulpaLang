Built into the language

The rules of the physical world, as syntax.

Other languages can control hardware, but their engineering constraints live in libraries and conventions. In Tulpa they're constructs the interpreter checks for you.

Units of measure

Quantities carry dimensions through every expression. Adding speed to distance is an error, not a silent bug.

0.5[m/s].to("km/h")

Contracts & fuzzing

Hehner-style require, ensure and invariant. tulpa verify fuzzes them and shrinks failures.

ensure result' >= 0[m]

State machines

States, guarded transitions, enter/exit hooks and history, with Mermaid diagrams from tulpa graph.

on gripped(m) if m <= 2[kg] => Idle

Reactive & timing rules

Edge-triggered when rules over signals, debouncing, and bounded-response deadlines on a virtual clock.

after t within 300[ms] ensure …

Safety envelopes

always monitors are checked after every device call, assignment and transition, then stop or run a handler.

always speed <= 2[m/s] else { … }

Hardware, simulated or real

GPIO, I2C, SPI, UART, PWM, Servo, PID, CAN and BLE. Deterministic simulation by default, Linux hardware with --hw.

--record run.tape · --replay run.tape

Contracts as test oracles

Let the toolchain find the counterexample

tulpa verify generates inputs that satisfy each require, checks every ensure, and shrinks a failure to a minimal case. Here it finds the off-by-threshold bug in clamp_speed straight away.

  • x' and result' refer to post-state values
  • Struct invariants are re-checked after writes and rolled back on violation
  • Exit code 1 on failure, so it drops straight into CI

Time as a language construct

Debounce and deadlines, declared

when … for debounces a condition, and after … within … ensure states a bounded-response requirement. With --virtual-time the clock is simulated, so timing behaviour is testable and deterministic.

  • The press is accepted at exactly 25 ms
  • The door never reports open, so the 300 ms deadline handler fires

Execution architecture

Prototype in a REPL. Ship native code.

The interpreter and VM run the whole language. Hot functions move to bytecode automatically, and the typed numeric subset compiles through LLVM into an object file and a C header for firmware.

TIER 1

Tree-walking interpreter

Runs the whole language and backs the REPL.

fib(30)
1.15 s
TIER 2 · default

Bytecode VM

Eligible functions compile on first call and fall back to the interpreter transparently.

fib(30)
0.28 s · about 4× faster
TIER 3 · tulpa build

LLVM native

Typed numeric code becomes an object or shared library plus a C header. Contracts stay as runtime checks.

fib(30)
0.005 s

Release-build benchmarks from the TulpaLang README. Every test runs under both the interpreter and the VM, and native output is differential-tested against the interpreter.

Verification, layered

Catch it before it reaches the motor.

  • Type and dimension checksGradual typing that includes unit dimensions.
  • Contracts, invariants and fuzzingExecutable specifications, plus tulpa verify.
  • Runtime safety envelopesMonitors that fail-stop or run a corrective handler.
  • Record and replayHardware sessions become regression tests without the rig.
  • Cycle-accurate RTLstd/rtl testbenches, checked bit-exactly and viewed as waveforms.

These mechanisms improve software verification. They aren't a formal proof or a safety certification. Read the scope notes.
